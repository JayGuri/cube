# HandCube Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use godmode:task-runner to implement this plan task-by-task.

**Goal:** Build HandCube, a browser-based app where a user manipulates five virtual twisty puzzles (3x3, Pyraminx, Skewb, Mastermorphix, Megaminx) via two-handed webcam gestures, with a guided "Academy" tutoring mode, following the reuse-vs-build decisions in `HandCube-Project-Plan-v2.md`.

**Architecture:** A single Vite + React + TypeScript SPA. Puzzle *logic* (state, legal moves, scrambling) is delegated to the `cubing` npm package wherever a WCA definition exists (cube3x3x3, pyraminx, skewb, megaminx); Mastermorphix reuses the cube3x3x3 logic under a different visual skin. Puzzle *geometry* is custom-built with `three-bvh-csg` cutting Three.js primitives, driven by a small per-puzzle cut-plane spec. Two genuinely new subsystems carry the project: a pure, camera-free-testable gesture finite-state-machine (MediaPipe HandLandmarker → semantic move events), and a data-driven Tutorial Engine that narrates and validates a fixed beginner method per puzzle. Every puzzle implements one `PuzzlePlugin` interface so the 2nd–5th puzzle are additions, not rewrites.

**Tech Stack:** React 18 + TypeScript + Vite, `cubing` (alg/kpuzzle/puzzles/scramble), Three.js + `@react-three/fiber` + `@react-three/drei`, `three-bvh-csg`, `@mediapipe/tasks-vision` (HandLandmarker), Zustand, Tailwind CSS v4, Framer Motion + `@react-spring/three`, `idb`, Vitest + Playwright, `vite-plugin-pwa`.

## Plan Review Notes (read this before executing)

This plan was written from `HandCube-Project-Plan-v2.md` (the authoritative spec — v1 is superseded) and then reviewed against it. Three deliberate deviations were made, plus two open risks that get resolved by a spike task instead of a guess:

1. **Flattened repo layout.** The spec's `handcube/apps/web/...` layout implies a monorepo, but there is only ever one app and no monorepo tool (pnpm workspaces / Turborepo) is specified anywhere. A monorepo shell around a single package is an unrequested abstraction (YAGNI). This plan puts the Vite app at the repo root instead: `src/`, `public/`, `tests/` directly under the project root. Every other path from the spec is preserved 1:1 below that point (e.g. `apps/web/src/core/puzzles/` → `src/core/puzzles/`).
2. **`cubing.js` API calls in the spec are approximate.** The spec's `puzzles["megaminx"].def()` dictionary-style call does not match the real, verified API. **RESOLVED by the Task 1.1 spike against cubing@0.56.0 — and this note was itself partly wrong.** `cubing/puzzles` exports only two named puzzle entries, `cube3x3x3` and `cube2x2x2`. Everything else — pyraminx, skewb, megaminx — is reached through the `puzzles` **dictionary**, so the spec's dictionary style was right for 4 of the 5 puzzles; only the `.def()` method name was wrong. Confirmed: `import { cube3x3x3, puzzles } from "cubing/puzzles";` then `await cube3x3x3.kpuzzle()` or `await puzzles["megaminx"].kpuzzle()` (ids: `3x3x3`, `pyraminx`, `skewb`, `megaminx`). Task 1.1 below is an explicit **API spike** — a throwaway script that prints the real method names from the installed package's TypeScript types — run *before* the `PuzzlePlugin` implementation is written, so the plugin code is built against confirmed APIs, not guesses. Do not skip Task 1.1.
3. **3x3 solver package choice is deferred to a spike, not locked in.** `cube-solver` (npm, Kociemba two-phase, by torjusti) exists and is real, but its exact facelet-string input/output format wasn't confirmed by research. Task 2.1 spikes this against a known scrambled state before Task 2.2 commits to writing the worker around it. `cubejs` is the documented fallback if `cube-solver`'s format is awkward to derive from a `KPattern`.
4. **CI/deployment and any GitHub remote are opt-in, not automatic.** Phase 0 sets up local git only. Creating a GitHub remote, pushing, and wiring Vercel/Netlify (spec §3, §14) are held in Phase 11 behind an explicit user go-ahead, per this session's safety rules on visible/shared-state actions.
5. **Lesson content is specified as a schema + a representative slice, not exhaustively authored for all five puzzles up front.** Full OLL/PLL-equivalent algorithm tables for five puzzles is unbounded content-authoring work, not an engineering unknown — the schema and the 3x3 track (Phase 5) prove the pattern end-to-end; Phases 6–8 note where each puzzle's method table plugs in, with 1–2 worked lesson steps each, and treat "fill in the rest of the table" as a content task the engineer executes directly against the schema, not as a design question.

Everything else below follows the v2 spec as written.

## Task 1.1 spike results — confirmed `cubing` API (v0.56.0, 2026-09-18)

These are measured, not assumed. Later tasks must use these names.

**Resolving a puzzle**
- `import { cube3x3x3, puzzles } from "cubing/puzzles"` — `cube3x3x3`/`cube2x2x2` are the ONLY named puzzle exports.
- Everything else: `puzzles["pyraminx" | "skewb" | "megaminx"]`. All 21 ids confirmed present.
- `await <entry>.kpuzzle()` → `KPuzzle`.

**KPuzzle** methods: `lookupOrbitDefinition, identityTransformation, moveToTransformation, algToTransformation, toTransformation, defaultPattern, canConvertDefaultPatternToUniqueTransformation`, plus `.definition` (`.orbits`, `.moves`).

**KPattern** methods: `toJSON, apply, applyTransformation, applyMove, applyAlg, isIdentical, experimentalToTransformation, experimentalIsSolved`.

**`isSolved` — read this before writing any plugin's `isSolved`:**
- `pattern.isIdentical(solved)` is exact: a whole-puzzle rotation (`y`) reads as **NOT solved**. Using it alone is a UX bug — a user who solves the cube while it is rotated gets told they failed.
- `pattern.experimentalIsSolved({ ignorePuzzleOrientation: true })` is rotation-tolerant and correct, **but only 3x3x3 supports it**. Skewb throws `"...not supported for this puzzle at the moment"`; assume pyraminx/megaminx do too until measured.
- Therefore: each plugin's `isSolved` tries `experimentalIsSolved` and falls back to `isIdentical`. Implemented once as a shared helper, not per puzzle.

**`patternData` shape** (what `pieceIdForFacelet`/Task 1.6 reads):
```
{ EDGES: { pieces: number[], orientation: number[] }, CORNERS: {...}, CENTERS: {...} }
```
Note the key is singular `orientation`. Solved = `pieces` is the identity permutation and `orientation` is all zeros. After `R`: `CORNERS.pieces = [4,0,2,3,7,5,6,1]`, `CORNERS.orientation = [2,1,0,0,1,0,0,2]`.

**Orbits — these confirm the plan's expected piece counts:**
| puzzle | orbits | total |
|---|---|---|
| 3x3x3 | EDGES(12x2) CORNERS(8x3) CENTERS(6x4) | 26 ✓ |
| pyraminx | EDGES(6x2) CORNERS(4x3) CORNERS2(4x3) | 14 ✓ (CORNERS2 = the trivial tips) |
| skewb | CORNERS(8x3) CENTERS(6x4) | 14 ✓ |
| megaminx | CORNERS(20x3) EDGES(30x2) CENTERS(12x5) | 62 ✓ |

**Scrambling** — `randomScrambleForEvent(event)` works for `333`, `pyram`, `skewb`, `minx`; all return in <250ms after warmup.
- `[...alg.childAlgNodes()]` yields **`Move` instances, not `Alg`**. Task 1.3's `node as unknown as Alg` cast is wrong. Wrap it: `new Alg([node])`, or use `pattern.applyMove(move)`. Move-by-move replay was verified identical to applying the whole alg at once.
- Megaminx scrambles use `R++`/`D--` notation and contain newlines.
- **Operational gotcha:** `randomScrambleForEvent` spawns a worker that keeps Node's event loop alive. A plain node/tsx script that calls it never exits without an explicit `process.exit(0)`. This will bite the Task 2.2 solver worker and any CI script.

**`Alg`**: `new Alg("R U")`, `.invert()` → `U' R'`, `.toString()`, `.childAlgNodes()` all confirmed.

```ts
import { cube3x3x3 } from "cubing/puzzles";
import { randomScrambleForEvent } from "cubing/scramble";
import type { Move, PuzzleState } from "../PuzzlePlugin";

const kpuzzlePromise = cube3x3x3.kpuzzle();
let solvedPattern: Awaited<ReturnType<typeof kpuzzlePromise["then"]>> extends never ? never : any = null;

export async function initCube3Logic() {
  const kpuzzle = await kpuzzlePromise;
  solvedPattern = kpuzzle.defaultPattern();
}

export function createInitialState(): PuzzleState {
  if (!solvedPattern) throw new Error("cube3 logic not initialized — call initCube3Logic() first");
  return { raw: solvedPattern };
}

export function applyMove(state: PuzzleState, move: Move): PuzzleState {
  const pattern = state.raw as any;
  return { raw: pattern.applyAlg(move.alg) };
}

export function isSolved(state: PuzzleState): boolean {
  const pattern = state.raw as any;
  return pattern.isIdentical(solvedPattern);
}

export async function scramble(): Promise<Move[]> {
  const alg = await randomScrambleForEvent("333");
  return [...alg.childAlgNodes()].map((node) => ({
    alg: node as unknown as import("cubing/alg").Alg,
    snapAngleDeg: 90,
  }));
}
```

```ts
import * as THREE from "three";
import { Brush, Evaluator, INTERSECTION } from "three-bvh-csg";

export interface CutPlane {
  normal: THREE.Vector3;
  offset: number; // signed distance from origin along normal
}

function halfSpaceBrush(plane: CutPlane, size: number, keepPositiveSide: boolean): Brush {
  // A big box, positioned/rotated so one face sits exactly on the plane,
  // representing "everything on the kept side of this plane".
  const box = new THREE.BoxGeometry(size, size, size);
  const brush = new Brush(box);
  const quat = new THREE.Quaternion().setFromUnitVectors(
    new THREE.Vector3(0, 0, 1),
    plane.normal.clone().normalize(),
  );
  brush.quaternion.copy(quat);
  const sign = keepPositiveSide ? 1 : -1;
  const center = plane.normal.clone().normalize().multiplyScalar(plane.offset + (sign * size) / 2);
  brush.position.copy(center);
  brush.updateMatrixWorld();
  return brush;
}

/**
 * Cuts `base` by every plane in `planes`, producing one piece per resulting
 * cell of the arrangement (2^n pieces worst case for n independent planes;
 * fewer if a cell is empty). Run once per puzzle type — never per move.
 */
export function cutSolidByPlanes(
  base: THREE.BufferGeometry,
  planes: CutPlane[],
): THREE.BufferGeometry[] {
  const evaluator = new Evaluator();
  const boundingSize = 100; // generously larger than any puzzle's base solid
  const cellCount = 2 ** planes.length;
  const pieces: THREE.BufferGeometry[] = [];

  for (let cell = 0; cell < cellCount; cell++) {
    let brush = new Brush(base.clone());
    brush.updateMatrixWorld();
    for (let p = 0; p < planes.length; p++) {
      const keepPositiveSide = ((cell >> p) & 1) === 1;
      const halfSpace = halfSpaceBrush(planes[p], boundingSize, keepPositiveSide);
      brush = evaluator.evaluate(brush, halfSpace, INTERSECTION);
      brush.updateMatrixWorld();
    }
```

```ts
import * as THREE from "three";
import { cutSolidByPlanes, type CutPlane } from "../../geometry/csgBuilder";
import type { PuzzleMesh } from "../PuzzlePlugin";

const AXES = [new THREE.Vector3(1, 0, 0), new THREE.Vector3(0, 1, 0), new THREE.Vector3(0, 0, 1)];

function cube3Planes(): CutPlane[] {
  const planes: CutPlane[] = [];
  for (const normal of AXES) {
    planes.push({ normal, offset: -0.5 });
    planes.push({ normal, offset: 0.5 });
  }
  return planes; // 6 planes -> up to 27 cells (3 per axis)
}

export function buildCube3Geometry(): PuzzleMesh {
  const box = new THREE.BoxGeometry(3, 3, 3);
  const pieces = cutSolidByPlanes(box, cube3Planes());
  // cutSolidByPlanes over 6 planes yields up to 2^6=64 cells; most are empty
  // (outside the box) and filtered already. The 27 surviving cells include
  // the fully-interior core piece (no colored facelets) — drop it: it's the
  // one piece whose bounding box doesn't touch any outer face.
  const visible = pieces.filter((geo) => touchesOuterFace(geo));
  return {
    pieces: visible.map((geometry, i) => ({ pieceId: `cube3-piece-${i}`, geometry })),
  };
}

function touchesOuterFace(geo: THREE.BufferGeometry): boolean {
  geo.computeBoundingBox();
  const box = geo.boundingBox!;
  const eps = 1e-4;
  return (
    Math.abs(box.min.x + 1.5) < eps || Math.abs(box.max.x - 1.5) < eps ||
    Math.abs(box.min.y + 1.5) < eps || Math.abs(box.max.y - 1.5) < eps ||
    Math.abs(box.min.z + 1.5) < eps || Math.abs(box.max.z - 1.5) < eps
  );
}

export const CUBE3_COLORS = {
  U: "#FFFFFF", D: "#FFD500", F: "#009E60", B: "#0051BA", R: "#C41E3A", L: "#FF5800",
};
```

```ts
import type { PuzzleState, PieceId } from "../PuzzlePlugin";

// Populate this once from kpuzzle.definition.orbits (via initCube3Logic-style
// lazy init) — maps a WCA-style facelet/corner label to the orbit name and
// slot index cubing uses internally. Fill in against the real shape confirmed

const FACELET_TO_ORBIT_SLOT: Record<string, { orbitName: string; slot: number }> = {};

export function pieceIdForFacelet(state: PuzzleState, facelet: string): PieceId {
  const pattern = state.raw as any;
  const { orbitName, slot } = FACELET_TO_ORBIT_SLOT[facelet];
  const permutation = pattern.patternData[orbitName].pieces[slot];
  return `cube3-${orbitName}-${permutation}`;
}

export function syncMeshToState(
  pieceIds: PieceId[],
  state: PuzzleState,
  allFacelets: string[],

  const facaletToPieceId = new Map<string, PieceId>();

    facaletToPieceId.set(facelet, pieceIdForFacelet(state, facelet));
  }
  return facaletToPieceId;
}
```

## Cross-cutting notes for the executing engineer

- **Test pyramid in practice:** puzzle logic and the gesture FSM get exhaustive Vitest unit coverage (they're pure functions — cheap to test exhaustively). Geometry gets piece-count/watertightness snapshot tests. Anything touching a real camera or a real deployed URL gets, at most, one Playwright E2E smoke test plus a manual verification note — don't try to unit-test MediaPipe itself.
- **Commit cadence:** one commit per TDD cycle (red → green → commit) as shown in every task above. Don't batch multiple tasks into one commit even when they land close together in time.
- **When a task's assumed third-party API name turns out wrong:** stop, fix every later task in this plan that references the same name (grep this plan file for it), don't patch just the one call site you're touching — the same root-cause-over-symptom principle applies to fixing a plan as to fixing code.
- **Puzzle count guardrail (spec §16):** do not begin Phase 7 until Phase 6's exit check is genuinely green (tests pass, lesson track present), and likewise Phase 8 until Phase 7's is. This is the single highest-leverage risk control in the whole project — it's tempting to parallelize puzzles once the pattern feels obvious, and that's exactly when a subtle geometry bug from Phase 6 gets copy-pasted into two more puzzles before anyone notices.
